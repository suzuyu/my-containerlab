# k02 → k04 の VIP／Egress 移行と k02 復帰

2026-09-25 実施。[手動手順](../../../tests/upgrade-rehearsal-runbook.md)に対応する初回リハーサル。
**VIP・別 Egress IP・同一 Egress IP の移行と旧アプリ復帰を確認した。
時間目標と短 timeout 条件の安定性は未達／未受入であり、全項目合格とはしない。**

## 対象と実施範囲

k02 は Kubernetes `1.35.5`、k04 は `1.36.4`、Cilium は両方 `1.20.1`。
k03 は DR 用 Mesh 接続を維持し、今回の移行先にはしなかった。
既存の業務アプリはないため、専用 namespace に A を両クラスタ各 2 Pod、比較用 B を k02 に 2 Pod 配備した。
入口 Service は local backend のみを選択し、Global Service によるクラスタ間転送は行わない。

| 項目 | 実装 |
|---|---|
| A の P | `172.16.14.20`／`fd21:0:0:14:0:0:1:100`、両 AF の同一 VIP |
| B の Q | `172.16.14.21`／`fd21:0:0:14:0:0:1:101`、旧クラスタの集約経路 |
| 優先度 | k02 current／LP 200、k04 candidate／100 → preferred／300 → off |
| E-A | k02 `172.16.24.101`／`fd21:0:0:24::101`、k04 `.104`／`::104` |
| E-B | `172.16.24.100`／`fd21:0:0:24::100` を旧・新の `worker` 間で単独移管 |
| E の所有 | 専用 dummy `uregress0`、Cilium Interface exact route と両 AF 別の Egress Policy |
| 外部確認 | ADC の既存 Fabric 端末と network namespace を共有する mock。socket の送信元を記録 |
| 観測 | ADC の継続測定、ADC／BDC の各段階の個別確認、両 BGR の属性・経路、Egress map |

共通 NAT は使用していない。Nexus は両 ADC BGR の一時 policy のみ変更し、BGW／Leaf は変更していない。
startup-config への試験設定保存は行っていない。
Cilium の Egress 有効化・復元は Agent／Operator の rollout を伴い、この準備区間には通信影響があった。
下記の切替時間は基盤準備後の値であり、今回の全作業を通じた無停止を意味しない。

## 機能の結果

1. k04 を candidate にしても、両 BGR は旧 k02 の LP 200 を選択した。
   新側の事前確認は NodePort `30260` で行った。これは今回の割当で、再実行時は再取得する。
2. VIP 単独で k04 へ切り替え、k02 に戻った。community と応答 cluster の関係を確認した。
3. E-A では P の入口を切り替えると外部送信元が E2 → E4、復帰時は E4 → E2 になった。
   両クラスタ・両 worker の Pod から指定 E での外部通信を確認した。
4. E-B は旧の業務 gate を閉じ、処理中件数 0 を確認して Policy／E の所有・広告を解除し、
   新へ E を付与した。両 BGR の E exact route は新 Gateway だけを指した。
   新の外部 probe 後に業務と P を公開し、同じ手順で E と P を k02 に戻した。
5. 旧が E を持ったまま新へ付与しようとすると、helper が変更前に拒否し、新側に interface が作られないことも確認した。
6. 比較用 B は、基準・切替・復帰の観測対象区間で `256/256` HTTP 成功、期待 cluster はすべて k02。
   Cilium feature の有効化中や profile 準備中の区間はこの数に含めない。

同一 E の逆移管後、旧 Pod の外部 probe は成功したが、VIP の個別確認は一度 `0/4` だった。
追加の経路・アプリ設定変更は行わず回復し、再確認は `4/4`、終了前の継続測定も 60 秒以上失敗なし。
この初回失敗を後続の成功で上書きしない。

## 時間の測定結果

ADC の A は両 AF 各 2 秒周期、B は各 10 秒周期。各 flow の未完了要求を積み上げず、再試行なし。
monitor の `urlopen(timeout=5)` は socket 操作の timeout であり、要求全体の上限ではない。
個別確認は curl の接続 3 秒／全体 5 秒で行い、継続測定と混同しない。
要求全体の実時間も記録し、5 秒を超えて成功したサンプルを消していない。

以下は操作イベントから期待した cluster／E の応答完了まで。値は **IPv4／IPv6、秒**。

| 操作 | 最初の期待応答 | 連続 3 成功の確認 | 観測区間の HTTP エラー数 |
|---|---:|---:|---:|
| VIP 単独：k02 → k04 | 1.77／2.91 | 5.14／5.90 | 0／0 |
| VIP 単独：k04 → k02 | 4.65／4.94 | 7.58／9.02 | 0／1 |
| 別 E：k02 → k04 | 3.96／4.53 | 9.18／10.59 | 0／0 |
| 別 E：k04 → k02 | 5.14／4.78 | 9.36／7.94 | 1／0 |
| 同一 E：新の VIP 公開 | 4.44／4.18 | 7.63／7.16 | 1／0 |
| 同一 E：旧の VIP 復帰 | 15.85／7.51 | 21.76／16.46 | 2／0 |

既存設計の「操作から連続 3 成功まで 5 秒以内」という提案目標は、この測定では未達。
2 秒周期自体が確認時刻へ影響するが、初回応答だけを使って合格へ置き換えない。
エラー数は各段階の観測時間が異なるため、単純な優劣・率の比較には使わない。
移行・復帰の各段階の HTTP 成功サンプルに、期待と異なる cluster／E の応答はなかった。
E-B の停止中にまだ旧応答が返ったサンプルは別の停止区間へ記録している。

### 同一 E の業務停止区間

| 操作 | 停止から最初の期待応答 | 停止から VIP 操作後の連続 3 成功 |
|---|---:|---:|
| k02 → k04 | 117.38／117.12 | 120.58／120.10 |
| k04 → k02 | 34.89／38.44 | 57.45／52.15 |

移行側には NodePort 確認の失敗後の再確認待ちを含む。IP 移管や BGP だけの収束時間ではなく、
手動手順と確認を含む業務再開時間である。停止中には意図した `503` と timeout／reset を観測した。

逆移管では、旧の gate を開けた時点で、残る集約経路から P に到達して旧応答が返った。
その後の exact route 復帰操作付近で失敗があり、最初の旧応答が出た時刻と継続して復旧した時刻は異なる。
**広告 off だけで入口を遮断できない**という設計上の注意を実測でも確認した。
停止全体の上限値は事前に合意していないため、上表をそのまま実測値として提示する。

### 通信失敗区間の回数と原因の確度

ADC の A の継続測定を要求開始時刻順に並べ、HTTP 成功で区切った連続失敗を 1 区間とする。
同じ計画停止で重なる IPv4／IPv6 の区間は 1 回にまとめた。時間は最初の失敗要求開始から
次の成功応答完了までであり、packet 単位の厳密な通信断時間ではない。準備区間と個別 curl は含めない。

| 試験 | 移行時の区間数 | 復帰時の区間数 | 最長の観測区間 |
|---|---:|---:|---:|
| VIP 単独 | 0 | 1 | IPv6、4.430 秒 |
| 別 E | 0 | 1 | IPv4、7.671 秒 |
| 同一 E | 1 | 2 | 移行時の IPv6、114.663 秒 |

合計 5 区間。AF ごとに別々に数える場合は IPv4 が 4、IPv6 が 3 の計 7 区間になる。
同一 E の復帰では計画停止による区間が最大 36.026 秒、その後の IPv4 の再失敗が 13.395 秒だった。
これらは切替後の監視期間中の失敗を含み、すべてを切替操作が直接引き起こしたとは断定しない。

| 観測 | 確認できたこと | 未確定のこと |
|---|---|---|
| 同一 E の長い停止 | 二重所有を避けるため業務 gate を閉じ、旧 E 解除、新 E 設定、probe、公開を順に実施した。手動確認と NodePort 再確認待ちを含む | IP 移管・BGP 収束・手動待ちそれぞれの所要時間の内訳 |
| 復帰時の一時回復と再失敗 | 集約経路経由で旧応答が先に返り、exact route 復帰操作付近で再失敗した | 再失敗が FIB 更新、戻り経路、接続状態、処理遅延のどこで発生したか |
| VIP 単独／別 E の散発失敗 | HTTP エラーを観測し、追加の経路・アプリ設定変更なしで回復した | BGP 更新、ホスト負荷、既知 checksum 課題のいずれが原因か |

最大 114.663 秒は監視上の失敗区間、120.576 秒は停止操作から連続 3 成功確認までで、基準点が異なる。
「BGP の収束に約 2 分かかった」という解釈はしない。切替前の checksum 正常 capture だけでは、
失敗した時刻・経路の checksum 問題を除外できない。
次回の原因調査では同じ timeout 条件を維持し、操作時刻、両 BGR の RIB／FIB、
入口と Egress の packet capture、Cilium drop／Egress map、ホスト負荷を時刻対応させる。
今回は原因を断定するための再試験や追加設定変更は行っていない。

## 失敗・制約と次の確認

- 準備中の mock IPv6 許可リストに誤った圧縮表記があり、正しい E2 を 2 回 `403` にした。
  許可リストを修正して成功。実装へ IP 正規化を追加し、localhost で送信元判定・拒否・冪等キー・IPv6 表記の 4 テストを実施した。
- k04 の初回 Egress probe は IPv4 が 1 回 timeout。経路収束後は同条件 `4/4` 成功。
- curl の各段階確認には散発的な失敗がある。echo-forward 初回 `3/4`、E-A 旧準備 `3/4`、
  E-A forward `3/4`、E-B 旧準備 `3/4`、E-B 新 NodePort 初回 `3/4`、E-B rollback 初回 `0/4`。
  保存した再確認と区別する。E-A forward の BDC IPv6 の短 timeout 安定性を合格とはしていない。
- 切替前の IPv6 連続確認は `6/6` 成功。ADC 受信 capture で checksum 正常 `230`、不正 `0`。
  offload 設定は変更していない。この範囲だけで既知 checksum／性能課題を解決済みとはしない。
- 継続測定の E-A／E-B 基準は約 110 秒／100 秒、両 AF と B の期待応答が成功。
  それでも操作後に timeout 等があるため、既知の `TI-004` と同一原因と断定せず、
  遅延・経路更新・両 BGR の実転送を追加で照合する。
- Cilium Egress と Mesh の公式非互換扱いは変わらない。今回の限定実験をサポート構成の保証にしない。
- DB／PVC の移行、Stateful の逆同期、ジョブの二重実行、長時間接続、DR 昇格、Node／Gateway 故障は未実施。
